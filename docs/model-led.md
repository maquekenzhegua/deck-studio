# 模型主导是怎么运作的

这份文档讲清楚一件事：**模型在这个产品里做什么、不做什么、出错时谁兜底。**
不是「接了个 API」，而是把「讲什么故事」这件事交给模型，把「数字对不对」留在程序手里。

---

## 一条链路，五个入口

```
材料 ──ingest──► Bundle ──compute──► Facts ──► ① 提角度  ──► ② 排页序 ──► ③ 自查
                                              │                              │
                                              └──────────► ④ 一句话改稿 ◄────┘
                                                                    │
                                                          ⑤ 评审 → 按意见改
                                                                    │
                                                              render2 ──► pptx
```

| 入口 | 端点 | 谁在决策 | 失败时 |
| --- | --- | --- | --- |
| ① 提角度 | `POST /api/ideas` | 模型读事实清单，给三种叙事角度（标题 / 角度 / 依据） | 409 提示先配模型；502 原样报错 |
| ② 排页序 | `POST /api/plan` | 模型选版式、绑事实、写标题与要点 | 超时 → 缩到 5 页重试 → 仍失败退回离线 |
| ③ 自查 | `plan()` 内部 | 模型按评审意见改一次 | 改坏数字就保留原稿 |
| ④ 改稿 | `POST /api/edit` | 模型读「当前大纲 + 一句话指令」重排 | 数字对不上整份作废，规则编辑器兜底 |
| ⑤ 评审 | `POST /api/edit`（指令「按评审意见改」） | 规则找问题，模型按清单改 | 无模型时规则编辑器试一次 |

---

## 为什么不让模型直接写 PPT

因为模型会编数字，而汇报里一个假数字就够了。

所以边界是硬的：

- 模型**只能引用** `f1…f24` 这样的事实 id，写不出事实之外的数；
- 渲染前 `deck/verify.py` 把每页文字里的数字逐个和事实比对，对不上就拦；
- `deck/agent.py` 收到模型稿后先跑 `review` + `verify`，`block` 级问题让模型改一次，改完仍对不上就整份退回离线稿——**宁可少一页，不出假数**。

模型负责的是「这一页该讲什么、用什么版式、标题怎么写」，程序负责「这个数字是不是真的、这页放不放得下」。

## 慢模型怎么办

真实测过的端点（`mimo-v2.6-flash`，约 28 token/s）：

| 动作 | 用时 | 结果 |
| --- | --- | --- |
| 提三个角度 | 113 s | 3 条，可直接选 |
| 排 9 页 | > 200 s | 读超时 |
| 自动缩到 5 页重试 | 约 280 s | 成功，5 页，review 0 问题 |
| 渲染 + 导出预览 | 5.3 s | 15 页 QA 100 |

因此有三条韧性：

1. **首稿预算** `240 s`：超过就跳过自查修订，先交付。
2. **页数降级**：`want → min(5, want)` 只重试一次，日志里写明「缩短篇幅重试」。
3. **`DECK_LLM_TIMEOUT`**：默认 200 s，可按端点调整；请求超时不会把窗口挂住十分钟。

界面上「页数」可以钉死 6 / 9 / 12；「自动」按事实条数估算（`min(7, 6 + facts//10)`），
给慢端点留出余量——想更深就手动选，代价是等更久。

## 模型稿长什么样

`/api/plan` 返回的 `plan` 就是渲染器吃的结构：

```json
{
  "deck_title": "增长押在一块区域上",
  "subtitle": "",
  "slides": [
    {"layout": "title",    "title": "增长押在一块区域上", "note": "…"},
    {"layout": "kpi_row",  "title": "华东同时是规模第一和增速第一的区域", "fact": "f13,f15,f17"},
    {"layout": "chart",    "title": "规模靠后的区域增速接近停滞", "fact": "f13", "variant": "waterfall"},
    {"layout": "table",    "title": "商机到方案漏得最多", "fact": "f16,f20"},
    {"layout": "closing",  "title": "接下来做什么", "bullets": ["…"]}
  ]
}
```

- `layout` 白名单在 `deck/plan.py:LAYOUTS`，未知版式回落 `bullets`。
- `chart` 可带 `variant`：`multi` 分面、`donut` 占比、`heatmap` 记分卡、`waterfall` 增量桥。
- `fact` 支持逗号分隔的多个 id，表格第二列会自动并排另一个测度。
- 任何 `{{f13}}` 占位符会在渲染时替换成真实数值——模型不必背数字，也就不会背错。

## 离线不是残废版

不填 Key 时走 `deck/compose.py`：按事实之间的比较选页、生成论点句、给出三条动作。
15 页、6 类图表、QA 100，全程本地、无网、无等待。

模型接上之后，**结构仍然受同一套规则约束**，区别只在措辞与叙事选择。
这也是为什么 154 条离线测试能覆盖大部分行为：规则是共享的。


## 写讲稿：把页面变成话

页面只解决「看什么」，讲稿解决「说什么」。点「写讲稿」，模型读一遍已经定稿的大纲，为每页写一句 20–70 字的口语，写进 PPTX 的备注页——导出的文件在任何放映器里都能看到。

规则只有一条硬约束：**讲稿里不许出现数字**。数字都在页面上，而散文没有校验器；带数字的句子直接丢弃，而不是想办法核对。写完的句子同时出现在大纲每一页的标题下面，讲者和听众看到的是同一份东西。

实测：15 页、14 句、16.9 秒（`mimo-v2.6-flash`）。


## 看一眼：让模型读自己排的页面

前面四步都在处理「说什么」，这一步处理「看起来怎么样」。结构校验只能证明数字对得上、文本框没越界；它不会发现一页虽然合法但视觉上死掉。视觉模型是流水线里唯一真正看见构图的读者。

- **只谈版式**：留白、对齐、字号对比、视线落点、图表可读性。内容对错由事实校验负责，模型的意见在那里只是噪声。
- **每条都要有修法**：「有点挤」不是问题描述，「把三条读法整体下移 0.3 英寸」才是。
- **看完就能改**：点「让模型按这些改」，意见会作为指令进入改稿流程，模型重排受影响的页面，然后重新校验数字。

视觉模型是独立设置：文本模型多是纯文本端点，拿它读图会在第一张 404，所以没填视觉模型时这个按钮不出现。页面会先缩到 960px 再上传，一次最多 8 页。
